### Критические (P0) — исправлены миграцией `supabase/migrations/20261013_security_hardening.sql`
1. Админ-RPC (`admin_set_role`, `admin_grant_stars`, `admin_set_pro`, `admin_set_ban`, …) доверяли параметру `p_actor_id` вместо `auth.uid()` — любой мог назначить себя владельцем.
2. Эти `SECURITY DEFINER`-функции были доступны роли `anon`.
3. RLS `user_profiles` позволяла пользователю самому выставить `is_pro`, `stars_balance`, `is_banned`.

**Миграцию нужно применить вручную** (см. «Что сделать»). Проверена на локальном PostgreSQL 16 на 6 вариантах схемы, применяется повторно без изменений, работает в одной транзакции.

### Главные исправления в приложении
- Белые экраны: `/topfocus`, `/notifications` (гость), все `/admin/*` (пустая страница) — исправлены; добавлен Error Boundary.
- Ложный успех: десятки мест, где ошибка Supabase игнорировалась и показывался «Сохранено» (задачи, привычки, цели, профиль, посты, админка).
- Даты: «сегодня» считалось по UTC (`toISOString`) — неверный день после полуночи по Москве; стрики привычек, календари, графики, финансы.
- Гонки и двойные нажатия: создание задач/целей/операций, отметка привычек, лайки, начисление звёзд.
- Финансы: суммы с запятой («12,50») теряли копейки; NaN/отрицательные значения; «этот месяц» включал будущие операции; балансы счетов не учитывали операции.
- Сессия: данные предыдущего пользователя оставались после выхода/смены аккаунта; вечный спиннер при сбое `getSession`.
- Мобильная вёрстка: нижняя панель перекрывала кнопки сохранения в модалках «Финансов» и редактировании профиля.
- Производительность: ленивая загрузка страниц — основной JS-бандл 1 591 КБ → 220 КБ (gzip 436 → 71 КБ); защита от «устаревших чанков» после деплоя.

## Открытые вопросы (нужно решение или доступ)
1. Реальная схема prod-БД не совпадает с SQL в репозитории (`user_stats`, `referral_codes`, `record_daily_active`, `posts.media_url`, бакеты storage, схема `stars_ledger`). Нужен дамп: `supabase db dump --schema public,storage`.
2. Финансы хранятся только в браузере (IndexedDB) — не синхронизируются между устройствами.
3. Повторяющиеся задачи сохраняются, но не повторяются; периоды привычек «Неделя/Месяц/…» не влияют на логику.
4. Достижения никогда не открываются (их никто не записывает); рейтинг «По рефералам» не работает под текущим RLS.
5. Звёзды начисляются клиентом (в пределах лимитов, введённых миграцией); полноценное решение — серверные RPC.
6. Кнопка покупки PRO и промокоды на странице PRO не подключены к оплате (теперь честно сообщают об этом).
7. `admin_set_ban` и промокоды без серверных CHECK на значения (клиент валидирует).
8. Баннер гостя «Данные сохранятся при входе» вводит в заблуждение — гость не может создавать записи.

## Что сделать владельцу
1. Сделать резервную копию БД (Supabase → Database → Backups).
2. Supabase → SQL Editor → вставить `supabase/migrations/20261013_security_hardening.sql` → Run. Прочитать NOTICE/WARNING. Откат описан в шапке файла.
3. Supabase → Authentication → URL Configuration: добавить `https://evgeniybutenko30-stack.github.io/JetFocus2/` в Site URL и Redirect URLs.
4. Влить ветку в `main` — GitHub Actions прогонит проверки и опубликует сайт только если всё зелёное.
5. После презентации: react-router 7, vitest 4, vite 6; серверные RPC для звёзд; синхронизация финансов.

Секреты: в репозитории найден только публичный anon-ключ Supabase (публичен по дизайну, ротация не нужна). Ключей `service_role` и других секретов нет.
